## Truth vocabulary (resolves four competing label schemes)

Three separate fields, never merged:

- **SourceClass** (where it came from): public, third_party, licensed, client, synthetic
- **ClaimClass** (how it is known): observed, sourced, inferred, assumed, synthetic, illustrative
- **DataMode** (what time it shows): live, snapshot, replay, scenario, synthetic_demo

## Slice B: canonical model, read scope and delegated limits (30 Oct 2026)

| ID   | Topic          | Decision                                                                                                                                                                                                                                                                                                                                                                                         |
| ---- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-64 | Read scope     | Every read of case data, and of anything that belongs to a case, is filtered on the server by clearance (highest classification per role: confidential for executive, analyst, expert, approver, auditor; restricted for operations owner and administrator) and by assigned sector workspaces (none assigned means all). Out-of-scope records answer 404, never 403, so existence does not leak |
| D-65 | Assigned work  | Operations owners see every handoff, including on cases above their clearance, because the work is assigned to them; the case itself stays out of scope                                                                                                                                                                                                                                          |
| D-66 | Workspaces     | Cases carry a sector workspace; cases opened from a signal inherit the signal's workspace; cases without one belong to the institution and stay visible within clearance                                                                                                                                                                                                                         |
| D-67 | Canonical data | Positions, managers and due-diligence records carry full provenance (source and record id, mode, classification, mapping version, quality, ingestion time). The demonstration rows are synthetic and agree with the cited exposure register (11 route-dependent holdings, 18% of NAV)                                                                                                            |
| D-68 | Limits         | Synthetic delegated limits per role and action class (Hedge: approver 20%, executive 40% of NAV; Reallocate: executive 10%; Defer: 90 and 180 days). Options carry a deterministic size; an approval above the decider's limit is blocked with the figures and a request to escalate; a limit with an unsized option blocks                                                                      |

## Slices C/D: connectors, ingestion and data quality (30 Oct 2026)

| ID   | Topic               | Decision                                                                                                                                                                                                                                                            |
| ---- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-69 | Connector registry  | Connectors are read-only by schema (`read_only` CHECK). Credentials are never stored: a connector names an environment variable (`auth_ref`) that holds them. Only the Governance Administrator registers, tests, pauses, resumes, retires, syncs or uploads        |
| D-70 | Adapters            | File, document, REST and RSS adapters run; webhook, SQL, SFTP and stream adapters are declared boundaries that refuse with a stated reason. Remote fetches are HTTPS only. A connector becomes "connected" only after an authenticated fetch succeeds               |
| D-71 | Metadata visibility | Amends D-64: administrators see every connector's metadata because they manage it; everyone else sees connectors within their clearance. The records a connector brings in remain filtered by each reader's clearance and workspaces                                |
| D-72 | Uploads             | Type checked by magic bytes, 10 MB and 5,000-row limits, stored under `UPLOAD_DIR` named by SHA-256. Rows are validated against a versioned mapping; rejected rows are kept as row-level issues (spreadsheet row numbers, header is row 1), never silently dropped  |
| D-73 | Source approval     | A connector's source must be approved before anything is ingested from it. Feed items arrive as unverified evidence and `new` signals in snapshot mode; never live. Failed syncs back off 2^n minutes                                                               |
| D-74 | Job queue           | pg-boss runs without its own migrations: migration 0008 creates its schema from pg-boss's construction plan so the non-owner role never needs CREATE; queue-management functions are SECURITY DEFINER with a pinned search path. `JOBS_ENABLED=false` disables jobs |
| D-75 | Data quality        | A data-quality view counts records by quality status and mode per dataset, lists failed, partial and warned runs, failed or paused connectors, stale sources and sources pending approval                                                                           |

| D-115 | Semantic registry         | `semantic-rules 1.0.0` (5A, FR-52). Engine metrics, situation measures and sector indicators are "system" definitions, defined by their versioned engine in code and never stored. Institution definitions and rules are stored (migration 0013, forced RLS), drafted by an analyst, domain expert or executive and approved by a domain expert or executive who is not the author (enforced in the API and by a database check); content is immutable, a change is a new version, and approving it retires the previous approved version. The five numeric mandate limits are seeded as approved, synthetic rules (M-RISK-02, M-RISK-03, M-RES-04, UTIL-FUEL-01, CPTY-LIMIT-01) with no named approver. Approved rules are evaluated on read from the latest scenario run and the sector models the reader may see, with value, headroom, source and record keys; with no readable input the result is "not evaluable", never a filler. Attention is raised within a stated margin of the threshold. The approved registry exports as JSON-LD (SKOS, Dublin Core and the `urn:tigeris:vocab:` vocabulary) without approver identities; exports are audited. The decision policy keeps using the scenario's mandate checks until 5C.                                                                                                      |
| D-116 | Intervention engine       | `intervention-engine 1.0.0` (5B, FR-53). Watch rules are versioned and approved by a second person like codified rules (migration 0014). Four kinds, one seeded per kind and owner-approved as synthetic: W-RULES (approved codified rules at attention or breach), W-SIGNALS (critical or elevated signals still new after 24 hours), W-CONNECTORS (connectors failing, or scheduled and not synced for 7 days), W-DRIFT (outcome reviews that missed). A sweep (on demand, after seeding, and every 15 minutes when background jobs are on) keeps one live intervention per rule key and subject: it raises new ones, refreshes recurring ones and marks cleared ones, but never closes one. Each intervention stores its rule version, inputs with references and the classification, sector and case it came from; the inbox filters by read scope (and the case's own scope) and by default shows what is routed to the reader's roles. Only routed roles acknowledge, resolve or dismiss; closing needs a reason of at least 10 characters; every action is audited. A closed intervention whose condition persists is raised again as a new one at the next sweep. Navigation gains "Intervention Inbox" after the Sovereign Overview group. Watch rules are drafted through the API; the screen lists, approves and retires them. |
| D-117 | Guardrails and monitoring | 5C (FR-54). A guardrail is recorded from an approved decision by the executive or that decision's approver, on the decision's action class (migration 0015): it blocks approval, or requires a named role, optionally only above a threshold in a stated unit, with an optional expiry. `decision-policy 1.2.0` checks every active, unexpired guardrail on approvals and names it in the reason; an option with no size, or a size in another unit, cannot be shown to be below a threshold, so the guardrail applies (fail closed). Guardrails are never edited: another executive lifts one with a reason; the recorder cannot lift their own. Everyone is bound by a guardrail; the decision it came from is shown only to readers of that case. Post-decision monitoring is watch kind `decision_monitor` (W-MONITOR, seeded, owner-approved synthetic): when a newer scenario run on a decided case puts an expected figure's central value outside the range expected at decision time, an intervention is raised (breach beyond one range width) and routed to the executive, approver and domain expert. Nothing is changed automatically.                                                                                                                                                                                       |
